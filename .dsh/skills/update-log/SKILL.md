# 每轮收尾：总结改动，并在够一次更新时发布程序更新日志（ORT一键报告）

## 0. 定位与范围

- 发布文件：根目录 `更新日志.md`（正序：旧 → 新，最新小节在文件末尾）；文件不存在时**新建**，并写入固定头部说明：
  `> 只记录程序本身的更新（新功能、行为/界面变化、缺陷修复、数据与设置格式变化、破坏性变化）。`
  `> 标题格式 ## YYYY-MM-DD（vX.Y.Z），用户未声明版本号时省略括号；按时间正序追加，最新一节在文件末尾。`
- **发布包自带更新日志**：`更新日志.md` 已登记在 `ORT一键报告.csproj`（`<None Include="更新日志.md">` + `<CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory>`），生成程序时会自动复制到输出目录（`bin\Debug\` / `bin\Release\`），发布包因此自带一份更新日志。不要移除这条登记；若用户要求更换日志文件名，必须同步改 csproj 里的这条 `None Include`。
- **只写程序更新内容**：ORT实验室管理系统的面向用户变化与影响运行的内部变化——新功能、行为/界面变化、程序缺陷修复、数据结构/数据库表/本机设置文件格式变化与迁移、破坏性变化（改名、路径调整、旧数据处理）。
- **不写仓库协作类改动**：skill（`.dsh/skills/`）、`AGENTS.md` 约定、提交/推送流程、构建脚本、验证脚本、截图、调试产物、纯文档整理——这些与程序运行无关，一律不进 `更新日志.md`。
- `修改记录.md`：历史变更记录，**用法保持原样**——本技能不为它新增规则，也不改写、删除、重排它的既有内容。
- 与 skill `git-commit-sync` 的分工：`update-log` 负责**写内容**，`git-commit-sync` 负责**提交推送**。顺序固定为
  **汇总改动 → （命中发布条件时）追加更新日志 → git-commit-sync（add → commit → push）**，
  保证更新日志进入本轮同一个 commit，不出现"日志留在工作区没提交"或"推送完再补一次"。
- 用户明确说「不要日志 / 先别提交 / 不要推送」时以用户指令为准。

## 1. 先确认本轮有没有改动

- 用 `git status --porcelain`（及 `git diff --stat`、必要时 `git diff --cached --stat`）拿到**真实**变更清单，不要凭记忆。
- 完全没有文件改动（且没有已暂存内容）→ 不写日志、不发布，最终回复写一行「本轮无文件变更，未提交」。
- 注意：构建产物、临时冒烟程序、日志文件若被 `.gitignore` 忽略，不算本轮改动。

## 2. 每轮有改动都要做的：总结「更新内容」

在本轮最终回复里给出简洁摘要（1~5 条），每条写"**改了什么 + 影响**"，例如
`- 计划表新增报告状态列：自动读取报告 TestStatus，全部测试项完成后显示「已完成」`。
不写「优化了体验」「完善了细节」这类空话，也不要把只讨论过、没落地的内容写成已完成。

这一步**只输出摘要，不落盘**；是否写进 `更新日志.md` 由第 3 步决定。若本轮改动全是仓库协作类（技能/约定/脚本/文档），摘要里注明「非程序改动，不进更新日志」。

## 3. 判断这一轮是否算「一次（程序）更新」

判定只看**程序改动**：非程序改动再多也不算一次更新。

**发布（满足任一即发布）**

- A. 用户明说：这是一次版本更新 / 发布更新日志 / 写更新日志 / 更新版本号 / 记一下这一版。
- B. 助手自判程序改动足够大，满足下面 ≥2 项：
  - 有面向用户的新功能、行为变化或界面改造；
  - 程序代码/资源变更文件 ≥ 3 个，或涉及 ≥ 3 个模块目录（`Main/`、`Plans/`、`Reports/`、`Admin/`、`Services/`、`Models/`、`Utils/`、`Resources`、`Themes/`、`Converters/`…）；
  - 数据结构/数据库表/本机设置文件格式变化，或需要数据迁移；
  - 破坏性变化（程序改名、路径调整、旧数据需要处理）；
  - 面向程序的更新条目 ≥ 5 条；
  - 修复了用户反馈的程序缺陷且影响用户可见行为。

**不发布（只做第 2 步摘要）**

- 只有文案/注释/日志/格式微调、纯构建或依赖变更、只读排查、纯提交同步；
- 只有 skill、`AGENTS.md`、构建/验证脚本、临时脚本、截图、调试产物等仓库协作类改动（如本技能自身的建立与调整）；
- 判定存疑时不要硬发，问用户一句「这一轮要不要作为一次版本更新记进更新日志？」

## 4. 发布：追加到根目录 `更新日志.md`

1. **读文件末尾**确认现有小节顺序与最新日期（用 read 工具；文件不存在则新建并写入第 0 步的头部说明）。
2. **日期**：取本机当天 `YYYY-MM-DD`。
   - 文件**末尾**已是同日期小节 → 直接在该小节末尾续写条目（不要新建重复标题）。
   - 否则在文件末尾追加新小节 `## YYYY-MM-DD`。
3. **版本号（仅当用户声明是版本更新时才写）**：标题写成 `## YYYY-MM-DD（vX.Y.Z）`。
   - 版本号来源只允许：用户口述，或用户要求同步时读 `Properties/AssemblyInfo.cs` 的 `AssemblyFileVersion`（当前 `1.0.2.0`）与 csproj 的 `ApplicationVersion`。
   - **不要自造版本号、不要自行自增版本**；用户要求同步程序版本号时才改 `AssemblyInfo.cs`。
4. **条目写法**：
   - `- **模块/功能名**：一句话说明改了什么、用户会看到什么变化（可附关键文件/类，如 `Services/PlanExcelService.cs`）。`
   - 一个逻辑单元一条；跨多文件的大功能用一条主条 + 缩进子条。
   - 只写真实改动；不复述 commit message；不写「已提交/已推送/本轮验证通过」这类过程信息；不写空话；不写技能与仓库约定类内容。
   - 与 `修改记录.md` 的紧凑写法保持一致的风格，但**面向用户的变化**优先，内部实现细节只保留必要的。
5. **保持文件结构**：头部说明行不动；**不改写、不删除、不重排**已发布的历史小节。只有用户明确要求「整理/压缩更新日志」时才编辑历史内容，且必须保留日期与要点。
6. 写文件只能走 write/edit 工具（UTF-8），禁止用 PowerShell 重定向写中文，避免编码损坏。

## 5. 收尾与汇报

- 写完日志立刻按 `git-commit-sync` 执行：`git add -A` → 中文 Conventional Commits 提交 → `git push origin <分支>`。commit message 保持以本轮功能为主，可在正文加一行说明已更新 `更新日志.md`。
- **发布版本时让发布包带上这次更新**：日志写完后再按 `AGENTS.md` 的命令生成一次程序（`MSBuild .\ORT一键报告.csproj … /t:Build`，需要全量时用 `/t:Rebuild`），根目录的 `更新日志.md` 会随生成复制到输出目录；用
  `(Get-FileHash '更新日志.md').Hash` 与 `(Get-FileHash 'bin\Debug\更新日志.md').Hash` 比对一致，确认发布包里的日志就是刚发布的那一份（Release 包同理比对 `bin\Release\更新日志.md`）。
  - 若 `ORT一键报告.exe` 正在运行，构建会在复制 exe 时报 `MSB3021/MSB3027`（与更新日志无关，日志这一项通常已复制成功）；关掉程序重新生成一次即可。
- 最终回复固定给出一到两行结果，例如：
  - 已发布：`本轮更新内容：…` + `已发布更新日志：2026-09-21（v1.2.0），追加到 更新日志.md（3 条）；已提交 <hash>，已推送 origin/master`
  - 有改动但未达发布条件：`本轮更新内容：…` + `未发布更新日志（程序改动未达一次更新）` + 提交/推送结果
  - 无改动：`本轮无文件变更，未提交`

## 硬性约束

- 绝不编造未发生的改动；不把讨论、计划、待办写成"已完成"。
- `更新日志.md` 只写**程序**更新内容；技能、`AGENTS.md`、脚本、纯文档等仓库协作类改动一律不写进去。
- 不改写、不删除 `修改记录.md` 的既有内容，也不用本技能的规则去约束它。
- 不为凑数发布更新日志；不重复发布同一轮。
- 更新日志与提交必须在同一轮内完成，不允许留到下一轮补。
- 不新建其他日志文件（`CHANGELOG.md` 等）；不擅自改动历史条目；不擅自改版本号。
