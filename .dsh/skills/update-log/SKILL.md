# 每轮收尾：总结改动，并在够一次更新时发布更新日志（ORT一键报告）

## 0. 定位与顺序

- 根目录**唯一**更新日志文件是 `修改记录.md`（正序：旧 → 新，最新小节在文件末尾）。不要另建 `CHANGELOG.md`、`更新日志.md` 等第二份文件，除非用户明确要求换文件。
- 与 skill `git-commit-sync` 的分工：`update-log` 负责**写内容**，`git-commit-sync` 负责**提交推送**。顺序固定为
  **汇总改动 → （命中发布条件时）追加更新日志 → git-commit-sync（add → commit → push）**，
  保证更新日志进入本轮同一个 commit，不出现"日志留在工作区没提交"或"推送完再补一次"。
- 用户明确说「不要日志 / 先别提交 / 不要推送」时以用户指令为准。

## 1. 先确认本轮有没有改动

- 用 `git status --porcelain`（及 `git diff --stat`、必要时 `git diff --cached --stat`）拿到**真实**变更清单，不要凭记忆。
- 完全没有文件改动（且没有已暂存内容）→ 不写日志、不发布，最终回复写一行「本轮无文件变更，未提交」。
- 注意：构建产物、临时冒烟程序、日志文件若被 `.gitignore` 忽略，不算本轮改动。

## 2. 每轮有改动都要做的：总结「更新内容」

在本轮最终回复里给出简洁摘要（1~5 条），每条写"**改了什么 + 影响**"，例如
`- 计划表新增报告状态列：自动读取报告 TestStatus，全部测试项完成后显示「已完成」`。
不写「优化了体验」「完善了细节」这类空话，也不要把只讨论过、没落地的内容写成已完成。

这一步**只输出摘要，不落盘**；是否写进 `修改记录.md` 由第 3 步决定。

## 3. 判断这一轮是否算「一次更新」

**发布（满足任一即发布）**

- A. 用户明说：这是一次版本更新 / 发布更新日志 / 记到修改记录 / 更新版本号 / 记一下这一版。
- B. 助手自判改动足够大，满足下面 ≥2 项：
  - 有面向用户的新功能、行为变化或界面改造；
  - 变更文件 ≥ 3 个，或涉及 ≥ 3 个模块目录（`Main/`、`Plans/`、`Reports/`、`Admin/`、`Services/`、`Models/`、`Utils/`、`Resources`、`Themes/`、`Converters/`…）；
  - 数据结构/数据库表/本机设置文件格式变化，或需要数据迁移；
  - 破坏性变化（程序改名、路径调整、旧数据需要处理）；
  - 本轮更新条目 ≥ 5 条；
  - 修复了用户反馈的缺陷且影响用户可见行为。

**不发布（只做第 2 步摘要）**

- 单行文案/注释/日志/格式调整、纯构建或依赖变更、只读排查、纯提交同步；
- 临时验证脚本、截图、调试产物；
- 新增/修改一个与用户产品行为无关的工程约定或工具文件（如本技能自身）。
- 判定存疑时不要硬发，问用户一句「这一轮要不要作为一次版本更新记进修改记录？」

## 4. 发布：追加到根目录 `修改记录.md`

1. **读文件末尾**确认现有小节顺序与最新日期（用 read 工具，不要用带编码坑的 `Get-Content` 直接写回）。
2. **日期**：取本机当天 `YYYY-MM-DD`。
   - 文件**末尾**已是同日期小节 → 直接在该小节末尾续写条目（不要新建重复标题）。
   - 否则在文件末尾追加新小节 `## YYYY-MM-DD`。
3. **版本号（仅当用户声明是版本更新时才写）**：标题写成 `## YYYY-MM-DD（vX.Y.Z）`。
   - 版本号来源只允许：用户口述，或用户要求同步时读 `Properties/AssemblyInfo.cs` 的 `AssemblyFileVersion`（当前 `1.0.2.0`）与 csproj 的 `ApplicationVersion`。
   - **不要自造版本号、不要自行自增版本**；用户要求同步程序版本号时才改 `AssemblyInfo.cs`。
4. **条目写法**（照抄文件既有风格）：
   - `- **模块/功能名**：一句话说明改了什么、用户会看到什么变化（可附关键文件/类，如 `Services/PlanExcelService.cs`）。`
   - 一个逻辑单元一条；跨多文件的大功能用一条主条 + 缩进子条。
   - 只写真实改动；不复述 commit message；不写「已提交/已推送/本轮验证通过」这类过程信息；不写空话。
5. **保持文件结构**：文件头部的说明行（`> 精简版：…`）不动；**不改写、不删除、不重排历史小节**。只有用户明确要求「整理/压缩修改记录」时才编辑历史内容，且必须保留日期与要点。
6. 写文件只能走 write/edit 工具（UTF-8），禁止用 PowerShell 重定向写中文，避免编码损坏。

## 5. 收尾与汇报

- 写完日志立刻按 `git-commit-sync` 执行：`git add -A` → 中文 Conventional Commits 提交 → `git push origin <分支>`。commit message 保持以本轮功能为主，可在正文加一行说明已更新 `修改记录.md`。
- 最终回复固定给出一到两行结果，例如：
  - 已发布：`本轮更新内容：…` + `已发布更新日志：2026-09-21（v1.2.0），追加到 修改记录.md（3 条）；已提交 <hash>，已推送 origin/master`
  - 有改动但未达发布条件：`本轮更新内容：…` + `未发布更新日志（改动未达一次更新）尚未发布` + 提交/推送结果
  - 无改动：`本轮无文件变更，未提交`

## 硬性约束

- 绝不编造未发生的改动；不把讨论、计划、待办写成"已完成"。
- 不为凑数发布更新日志；不重复发布同一轮。
- 更新日志与提交必须在同一轮内完成，不允许留到下一轮补。
- 不新建第二份更新日志文件；不擅自改动历史条目；不擅自改版本号。
