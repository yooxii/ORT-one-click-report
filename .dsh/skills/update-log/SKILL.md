# 每轮收尾：总结改动，并在够一次更新时发布程序更新日志（ORT一键报告）

## 0. 定位与范围

- 发布文件：根目录 `更新日志.md`；**按版本分节**（标题 `## <版本号>`，如 `## 0.3`），新版追加在文件末尾，最新版在最下方。文件不存在时新建，并写入固定头部说明：
  `> 按版本记录程序本身的更新：新功能、行为/界面变化、缺陷修复、数据与设置格式变化、破坏性变化。`
  `> 每版一节，标题为 ## <版本号>；只写功能与行为变化，不写代码、文件、构建、测试等实现细节。`
- **发布包自带更新日志**：`更新日志.md` 已登记在 `ORT一键报告.csproj`（`<None Include="更新日志.md">` + `<CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory>`），生成程序时会自动复制到输出目录（`bin\Debug\` / `bin\Release\`），发布包因此自带一份更新日志。不要移除这条登记；若用户要求更换日志文件名，必须同步改 csproj 里的这条 `None Include`。
- **只写程序更新内容**：ORT实验室管理系统的面向用户变化与影响运行的变化——新功能、行为/界面变化、程序缺陷修复、数据结构/数据库表/本机设置文件格式变化与迁移、破坏性变化（改名、路径调整、旧数据处理）。
- **不写实现细节**：不写文件名/类名/方法名/字段名，不写"代码清理""重构了 XX 类""新增单元测试""升级依赖""编译警告"这类与功能无关的条目，不写提交、构建与验证过程。
- **不写仓库协作类改动**：skill（`.dsh/skills/`）、`AGENTS.md` 约定、提交/推送流程、构建脚本、验证脚本、截图、调试产物、纯文档整理——这些与程序运行无关，一律不进 `更新日志.md`。
- `修改记录.md`：历史变更记录，**用法保持原样**——本技能不为它新增规则，也不改写、删除、重排它的既有内容。
- 与 skill `git-commit-sync` 的分工：`update-log` 负责**写内容**，`git-commit-sync` 负责**提交推送**。顺序固定为
  **汇总改动 → （命中发布条件时）追加更新日志 → git-commit-sync（add → commit → push）**，
  保证更新日志进入本轮同一个 commit，不出现"日志留在工作区没提交"或"推送完再补一次"。
- 用户明确说「不要日志 / 先别提交 / 不要推送」时以用户指令为准。

## 1. 先确认本轮有没有改动

- 用 `git status --porcelain`（及 `git diff --stat`、必要时 `git diff --cached --stat`）拿到**真实**变更清单，不要凭记忆。
- 完全没有文件改动（且没有已暂存内容）→ 不写日志、不发布，最终回复写一行「本轮无文件变更，未提交」。
- 注意：构建产物、临时冒烟程序、日志文件若被 `.gitignore` 忽略，不算本轮改动。

## 2. 每轮有改动都要做的：总结「更新内容」

在本轮最终回复里给出简洁摘要（1~5 条），每条写"**改了什么 + 影响**"，例如
`- 计划表新增报告状态列：自动读取报告 TestStatus，全部测试项完成后显示「已完成」`。
不写「优化了体验」「完善了细节」这类空话，也不要把只讨论过、没落地的内容写成已完成。

这一步**只输出摘要，不落盘**；是否写进 `更新日志.md` 由第 3 步决定。若本轮改动全是仓库协作类（技能/约定/脚本/文档），摘要里注明「非程序改动，不进更新日志」。

## 3. 判断这一轮是否要发版本：**只看用户有没有主动提出**

- **版本发布权在用户手上**：用户明说「这是一次版本更新 / 发布 0.6 / 写更新日志 / 更新版本号 / 记一下这一版」时才发布（写 `更新日志.md` 的版本小节 + 改版本号 + 打包）。
- **不要自作主张**：不再按改动量、模块数、条目数（例如「累积满 10 条」）推断该不该发布；用户没提，本轮就**只做第 2 步的「更新内容」摘要**，不写 `更新日志.md`、不改版本号。
- 判定存疑时问一句「这一轮要不要作为一次版本更新记进更新日志？」，不要硬发。

## 4. 发布：追加到根目录 `更新日志.md` 并同步版本号

1. **读文件末尾**确认已有哪些版本（用 read 工具；文件不存在则新建并写入第 0 步的头部说明），拿到**最新版本号**。
2. **版本号**：
   - **由用户指定**（如「发布 0.6」→ 标题写 `## 0.6`）。
   - 用户只说「这是一次版本更新」没给号 → 用用户措辞里的号；实在没有才问一句，**不要自行 +0.1**。
   - 文件里还没有任何版本节（首次发布）→ 必须用用户指定的版本号；用户没给就问一句，不要自己起头。
   - 用户要求「从某版开始的所有更新统一到某版」→ 把该版之后的版本小节条目**并入**该版本、删掉多余标题，功能要点一条都不能丢。
   - **版本号三处必须一致**：`更新日志.md` 的版本小节、`Properties/AssemblyInfo.cs` 的 `AssemblyVersion`/`AssemblyFileVersion`、csproj 的 `ApplicationVersion`。主界面显示的版本号取自程序集版本，只改日志不改程序集，用户就会看到版本号没跟着变（曾经发生过）。
3. **条目写法**：
   - `- **功能名**：一句话说明改了什么、用户会看到什么变化。` 一条一个功能。
   - **不写实现细节**：不写文件名、类名、方法名、字段名；不写代码清理/重构/单元测试/依赖/构建/警告；不写「已提交/已推送/验证通过」。
   - **只写功能与行为变化**（含用户可见的缺陷修复，通常合并成一条「修复」）。
4. **压缩与去重（每次写入都要做）**：
   - 写新条目前先扫一遍已有条目：同一功能的既有条目直接**改写合并**，不新增重复条目；同一功能的多次演进只保留**最终形态**（例如"勾选框控制回线工令"后来被"单体去向驱动"取代，旧写法删掉）。
   - 措辞尽量短：一条一句话，能合就合（纯可用性小改可并为一条「其他改进」）。
5. **保持文件结构**：头部说明行不动；已发布的版本小节不改写、不重排，除非用户明确要求「整理/压缩更新日志」或「统一到某一版」——此时允许合并、改写、删除重复与过时条目，但不得丢失功能要点。
6. 写文件只能走 write/edit 工具（UTF-8），禁止用 PowerShell 重定向写中文，避免编码损坏。

## 4.1 发布打包（用户提出发布时一并做）

- 跑 `tools/make-release.ps1`：重新生成 Release → 按原目录结构打包（含 `Data\local_settings.json`）→ 输出 `bin\ORT实验室管理系统_<主.次>.zip`，包内顶层目录同名。
- 打包前确认没有 `ORT实验室管理系统.exe` 在运行，否则 Release 生成覆盖 exe 会失败。
- 该脚本含中文，**必须保留 UTF-8 BOM**；用 write/edit 改过它之后要补回 BOM，否则 PowerShell 5.1 会按 ANSI 读成语法错误。

## 5. 收尾与汇报

- 写完日志立刻按 `git-commit-sync` 执行：暂存 → 中文 Conventional Commits 提交 → `git push origin <分支>`。commit message 保持以本轮功能为主，可在正文加一行说明已更新 `更新日志.md` 与已打包。
- **发布时让发布包带上这次更新**：日志与版本号都改完后再跑 `tools/make-release.ps1`（它内部重新生成 Release，根目录 `更新日志.md` 会随生成复制到 `bin\Release\`），脚本会自检日志哈希与 `Data\local_settings.json` 是否一致/在包内。
  - 若 `ORT实验室管理系统.exe` 正在运行，构建会在复制 exe 时报 `MSB3021/MSB3027`（与更新日志无关，日志这一项通常已复制成功）；关掉程序重新生成一次即可。
- 最终回复固定给出一到两行结果，例如：
  - 已发布：`本轮更新内容：…` + `已发布 0.5：更新日志与程序版本号三处同步，发布包 bin\ORT实验室管理系统_0.5.zip；已提交 <hash>，已推送 origin/master`
  - 有改动但用户没提出发布：`本轮更新内容：…` + `未发布版本（等你确认发布）` + 提交/推送结果
  - 无改动：`本轮无文件变更，未提交`

## 硬性约束

- 绝不编造未发生的改动；不把讨论、计划、待办写成"已完成"。
- `更新日志.md` 只写**程序功能与行为变化**：不写日期、不写实现细节（文件/类/方法/测试/构建/依赖）、不写技能与仓库约定类改动。
- 版本号按第 4 步规则来：**由用户主动提出并指定**，不自行 +0.1、不按改动量推断；改版本号时 `更新日志.md`、`AssemblyInfo.cs`、csproj 三处一起改。
- 写入前必须查重：同功能只保留一条、只保留最终形态。
- 不改写、不删除 `修改记录.md` 的既有内容，也不用本技能的规则去约束它。
- 不为凑数发布更新日志；用户没提出发布就不写 `更新日志.md`；不重复发布同一轮。
- 更新日志与提交必须在同一轮内完成，不允许留到下一轮补。
- 不新建其他日志文件（`CHANGELOG.md` 等）。
